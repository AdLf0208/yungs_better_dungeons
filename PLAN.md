Two engine facts decide the shape:

- `crates/horizon-world/src/worldgen/structure/processor.rs:748-800` refuses an unknown
  `processor_type` (`DecodeError::Field`), so the jar's processor lists are **fatal** if carried
  as data. The mod's 11 processor types exist only as Java classes (the public source, read as
  analysis, is `YUNG-GANG/YUNGs-Better-Dungeons` v6.1.1 + `YUNGs-API` v5.1.9).
- the SDK's `StructureType`/`StructurePiece`/`StructuresRegistrar` (`world/structure_type.rs`,
  `parts/structures.rs`) is the sanctioned route: a mod registers a type, a data-pack structure
  with `"type": "betterdungeons:…"` is generated by that type.

## Shape

One SDK package: a registered `StructureType` whose `find_generation_point` runs a **pure**
jigsaw assembly (`runtime::assemble`) over **generated** tables (templates, pools, processor
lists, structure config), and `StructurePiece::post_process` applies the decoration chain and
writes the blocks of the chunk it is asked about.

- `src/templates.rs` (generated by `tools/gen_tables.py`): every palette state of the 16
  templates, every block, every jigsaw connector (pool/name/target/final_state), and the
  processor-generated states (candles, chains, etc.). No binary parsing at runtime, no crate.
- `src/pools.rs` (generated): both pools with the jar's weights/order/`max_count`/`name`, the
  four processor lists in the jar's order with their parameters, and the structure config
  (`start_pool`, `start_jigsaw_name`, `size` 10, `start_height` uniform −50..50,
  `max_distance_from_center` 80, `use_expansion_hack` false).
- `src/runtime.rs` (pure, no `mod_api` types): shuffle/weighted draws, jigsaw `can_attach`,
  rotation + rotation of every state property the palette carries, bounding boxes, the max-count
  and depth caps, the maximum-bounds check, the 12 processor behaviours as pure decisions over a
  `WorldView` trait, chest/banner structure-wide counters, status readout. Tests.
- `src/support.rs` (glue): the registrar call (`register_structure_type`, `block_key` per
  state), `StructureType::find_generation_point` (decode `context.config()`, build `BlockState`s
  from `context.metadata()`, run `runtime::assemble`), `StructurePiece::post_process` (write),
  save/load, and `/betterdungeons status`.

## Content carried (and what is not)

Loadable data (byte-identical to the jar): 16 `.nbt`, `loot_table/small_dungeon/chests/
loot_piles.json`, `tags/worldgen/biome/has_structure/small_dungeon.json`, `structure_set/
small_dungeons.json`, and `worldgen/structure/small_dungeon.json` with **only** `type` rewritten
to `betterdungeons:small_dungeon_type`.

Not loadable, kept verbatim under `carry-work/jar/` as evidence (the port's Rust tables are the
loadable form, and `tools/check_content.py` proves table ≡ jar): both template pools and the four
processor lists — their `yungsapi:yung_single_element` element type and `betterdungeons:*`
processor types are what the engine refuses.

1.21.1 → 26.3 block renames in the palette are mapped in the generated states
(`minecraft:chain` → `minecraft:iron_chain`), and the generator refuses any name the 26.3
registry does not have.

## Dropped (recorded, not silent)

- the other five structures, the aggregate `better_dungeons` structure, the two
  `remove_*_feature_in` biome modifiers;
- `start_jigsaw_name`'s `/locate` semantics beyond the anchor offset, the vanilla `JigsawJunction`
  record (only terrain adaptation reads it — this structure declares none);
- `project_start_to_heightmap` / `use_expansion_hack` / non-rigid projections (absent or false
  in the carried JSON; a non-rigid element refuses the piece instead of guessing);
- the config file (`bannerMaxCount` 2, `chestMin/MaxCount` 1/2, `enableHeads`, `enableNetherBlocks`,
  `enableOreProps` true) — the defaults are compiled in, the config screen is not ported.
